## Findings

### Finding 1: Oracle price manipulation via flash-loaned coin balances — `Karma.sol:112-127`

- Severity: Critical
- Confidence: 0.95
- Category: oracle_manipulation
- Description: `submitPrice()` reads the caller's bull/bear coin balances and the coins' `priceSell()` at the instant of the call. An attacker can use a flash loan to temporarily acquire large, perfectly balanced bull and bear coin positions within a single transaction, submit a manipulated price with maximum weight, then return the coins — all in one atomic transaction. Because the weight is directly derived from these spot balances and spot prices (via `WeightLib.computeWeight`), the attacker can dominate the oracle's weighted average and set an arbitrary price.
- Exploit Scenario: Attacker flash-borrows a large amount of the base token, buys equal amounts of bull and bear coins to maximize their neutrality weight, calls `submitPrice()` with a price far from the real market price, then sells the coins back and repays the flash loan. If the Karma oracle feeds a `PredictionPool.rebalance()`, the manipulated price transfers reserves from one coin to the other, and the attacker profits from the mispriced coin.
- Recommendation: Record weights based on a time-weighted average position (TWAP of balances) rather than instantaneous spot balances. Alternatively, require that balances have been held for a minimum duration (e.g., check that the balance existed at a previous block using a snapshot mechanism or a minimum hold time) before a submission is accepted.

### Finding 2: Rebalance can be called by anyone to front-run oracle updates — `PredictionPool.sol:190`

- Severity: High
- Confidence: 0.85
- Category: access_control
- Description: `rebalance()` is a fully public function with no access control. It reads the oracle's current price and shifts reserves between bull and bear coins. Combined with a manipulable Karma oracle (Finding 1), or even with a Chainlink oracle, any MEV bot or attacker can sandwich oracle price updates: call `rebalance()` immediately after an oracle update to capture the maximum reserve transfer, after buying the advantaged coin beforehand.
- Exploit Scenario: An attacker monitors pending Karma `submitPrice()` or Chainlink price update transactions. Before the update, the attacker buys the coin that will benefit. After the oracle update lands, the attacker (or a bot) calls `rebalance()` which shifts reserves favorably, increasing the value of their position, then sells immediately.
- Recommendation: Consider limiting `rebalance()` so it can only be called as part of a `buy()` or `sell()` flow (it already is via `IPoolRebalance`), and remove or guard the standalone external access. If public rebalancing is intentional (see Notes), at minimum document the MEV risk so pool creators understand it.

### Finding 3: Stale Chainlink price accepted without staleness check — `ChainlinkOracle.sol:24-25`

- Severity: High
- Confidence: 0.9
- Category: oracles_external_data
- Description: `readValue()` checks that `answer > 0`, `updatedAt != 0`, and `answeredInRound != 0`, but never checks whether the data is stale. There is no comparison of `updatedAt` against `block.timestamp` with a maximum staleness threshold. If the Chainlink feed stops updating (e.g., the feed is deprecated, the L2 sequencer is down, or network congestion delays updates), the oracle will continue returning a potentially very stale price as if it were current.
- Exploit Scenario: A Chainlink feed stops updating for hours. The `ChainlinkOracle` continues returning the last price. `PredictionPool.rebalance()` uses this stale price to transfer reserves. If the true market price has moved significantly, this causes incorrect reserve distributions, and a trader aware of the stale feed profits by buying the undervalued coin.
- Recommendation: Add a configurable `maxStaleness` parameter to the constructor. In `readValue()`, revert if `block.timestamp - updatedAt > maxStaleness`. For L2 deployments, also consider checking the sequencer uptime feed.

### Finding 4: Missing `roundId >= answeredInRound` check in Chainlink oracle — `ChainlinkOracle.sol:24`

- Severity: Medium
- Confidence: 0.8
- Category: oracles_external_data
- Description: The Chainlink `latestRoundData()` response includes both `roundId` and `answeredInRound`. The code unpacks `roundId` as `_` (discarded) and does not verify `answeredInRound >= roundId`, which is the Chainlink-recommended check to ensure the answer was actually computed in the current or a later round. Without this, a price from a previous round that has not been fully updated could be accepted.
- Exploit Scenario: During a period of Chainlink network instability, a round's answer may carry over from a much older round. Without the `answeredInRound >= roundId` check, this stale answer passes validation and is used as the current price.
- Recommendation: Add `if (answeredInRound < roundId) revert InvalidPrice();` to `readValue()`.

### Finding 5: `Coin.buy()` price calculation uses `Rounding.Ceil` — favors buyer, coins minted exceed reserve backing — `Coin.sol:175-177`

- Severity: Medium
- Confidence: 0.75
- Category: arithmetic_logic
- Description: In `buy()`, the number of coins minted (`amountCoin`) is computed using `Math.Rounding.Ceil` — rounding up. This means the buyer receives slightly more coins than the deposited assets strictly back. Over many small transactions, this rounding consistently favors the buyer over the protocol. Since `priceBuy()` already rounds up (Ceil) to protect the protocol, applying Ceil again on the division `amountAfterFees / price` double-favors one direction. The coin supply will gradually exceed its reserve backing, creating a small shortfall that grows with transaction volume.
- Exploit Scenario: An attacker makes many minimum-sized buy transactions, each receiving 1 extra wei of coins from rounding. Over thousands of transactions, the cumulative rounding error creates a measurable gap between the coin supply and the backing reserves. The last sellers bear this cost as the reserve cannot fully back all outstanding coins.
- Recommendation: Change the rounding in `buy()` line 175–177 from `Math.Rounding.Ceil` to `Math.Rounding.Floor` (or remove the rounding argument, which defaults to Floor). `priceBuy()` already rounds Ceil to protect the protocol; the coin amount calculation should round Floor to ensure the buyer never receives more coins than the assets strictly justify.

### Finding 6: `AccumulatorVault.flushToken()` reverts on zero balance — `AccumulatorVault.sol:59-63`

- Severity: Low
- Confidence: 0.85
- Category: denial_of_service
- Description: `flushToken()` calls `safeTransfer(devFeeReceiver, amount)` where `amount` is the full balance. If the balance is zero, many ERC-20 implementations (especially those that revert on zero-amount transfers) will cause this call to revert. While this does not lock funds, it is a nuisance: the dev cannot flush a token that has a zero balance without the transaction reverting. Some tokens revert on zero-amount transfers per their implementation.
- Exploit Scenario: The `dev` calls `flushToken()` for a token that has a zero balance (e.g., it was already flushed, or no fees arrived yet). The transaction reverts because the underlying ERC-20 rejects a zero-amount transfer. This is a minor DoS — the dev simply has to wait until a non-zero balance accrues.
- Recommendation: Add an early return if `amount == 0` before the `safeTransfer` call.

### Finding 7: `Karma.latestRoundData()` unsafe uint256-to-int256 cast — `Karma.sol:202`

- Severity: Medium
- Confidence: 0.8
- Category: arithmetic_logic
- Description: `latestRoundData()` casts `price` (a `uint256`) to `int256` via `answer = int256(price)`. The weighted average price is a WAD-scaled (1e18) value. If the weighted average price exceeds `type(int256).max` (~5.78e76), this cast silently wraps to a negative number. While prices this large are unlikely in normal operation, a manipulated oracle (see Finding 1) could push the price to extreme values. Chainlink-compatible consumers that check `answer > 0` would then reject the data, causing integration failures. Additionally, `submissionCount` is cast to `uint80` without overflow checking — if more than 2^80 submissions occur, the roundId wraps.
- Exploit Scenario: An attacker with enough weight submits an astronomically large price. The weighted average eventually exceeds `type(int256).max`. Any Chainlink-compatible consumer calling `latestRoundData()` receives a negative `answer`, breaking integrations that depend on `answer > 0`.
- Recommendation: Add a bounds check before the cast: `if (price > uint256(type(int256).max)) revert PriceOutOfBounds();`. For `submissionCount`, consider capping or checking `submissionCount <= type(uint80).max`.

## Notes

### Note 1: Public `rebalance()` is intentional design — `PredictionPool.sol:190`

- Category: design-tradeoff
- Observation: `rebalance()` has no access control. Any address can trigger a reserve rebalance at any time. This exposes the pool to MEV sandwich attacks around oracle updates.
- Rationale: The code intentionally makes `rebalance()` public so that `Coin.buy()` and `Coin.sell()` can call it via the `IPoolRebalance` interface. Public rebalancing is a documented design decision that ensures the pool stays balanced without relying on a privileged keeper. The MEV risk is a known trade-off for permissionless operation.

### Note 2: Owner can change oracle without timelock — `PredictionPool.sol:181-188`

- Category: accepted-risk
- Observation: The pool owner can call `updateOracle()` at any time to point the pool at a different oracle. This could redirect the pool to a manipulated oracle. However, this is a standard owner pattern using Ownable2Step (two-step transfer), meaning ownership transfer requires acceptance by the new owner.
- Rationale: The use of `Ownable2Step` and the `onlyOwner` modifier is a deliberate access-control model. The owner is the `vaultCreator` who set up the pool. Adding a timelock would be a defense-in-depth improvement but its absence is a design choice, not an oversight.

### Note 3: Fee rounding uses `Ceil` consistently in `_fees()` — `Coin.sol:271-273`

- Category: design-tradeoff
- Observation: All three fee components (vault, dev, creator) are rounded up with `Math.Rounding.Ceil`. This means users pay slightly more fees than the exact percentage on small amounts, and the total of fees extracted can exceed the mathematical percentage of the amount. Combined with the `totalFees >= amountAsset` check (line 173, 226), this prevents a rounding edge case from zeroing out the post-fee amount.
- Rationale: Rounding fees toward the protocol is a standard defense against rounding-to-zero attacks. This is an intentional design pattern.

## Limitations

**Standing limitations:**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations:**

- The `WadExp.sol` library is vendored from Solady. The implementation was not re-audited against the upstream commit hash noted in its comments — it was taken as trusted based on the provenance claim.
- OpenZeppelin library code (imported via `@openzeppelin/contracts/`) was not reviewed. Only the project's own code was analyzed.
- The test files (`test/` directory) were not reviewed as the security-review skill excludes findings in test files.
- No on-chain state was examined. Deployed parameter values (actual fee percentages, tau, minTotalBalance) could affect the practical exploitability of some findings but were not available.
- Flash-loan exploitability (Finding 1) depends on the specific DeFi ecosystem where these contracts are deployed (availability of flash-loan providers, DEX liquidity for bull/bear coins). The attack path was described in general terms.
